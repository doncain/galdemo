--------------------------------------------------------
 先理解它是怎么工作的（30 秒，理解了就不会做错）
--------------------------------------------------------

楼层文本 → 正则替换成一段代码块 → 酒馆助手提升为 iframe
        → iframe 里 $.load(某个 URL) → 拉单文件 HTML → 渲染成画面

那个 URL 就是 CDN 地址，形如：

  https://cdn.jsdelivr.net/gh/<用户名>/<仓库名>@<commit-sha>/dist/yaoguai/minigal/index.html

★ 注意 `@` 后面跟的是**提交号**，不是 `master`。
  这是刻意的——用分支名会让 CDN 长期返回旧版本，原因见文末「日常更新」一节。
  下面为便于理解先按 `@master` 讲，最终一定要换成提交号。

三个关键点：

  ① jsDelivr 自己不做托管。它只做一件事：把 GitHub 仓库的文件
     按路径映射成一个带缓存的 URL。所以「发布」= 把文件推到 GitHub，
     没有别的魔法，也不需要注册 jsDelivr 账号。

  ② `@` 后面那一段（版本标识）之后是**仓库内的文件路径**，必须与构建产物完全一致：
       dist/yaoguai/minigal/index.html
     路径写错 = CDN 返回 404 = 酒馆里一片空白。

  ③ 仓库必须是 **公开（Public）**。私有仓库的 CDN 地址拉不到，
     这是新手最常踩的坑。


========================================================
 第一步：在 GitHub 建一个空仓库
========================================================

  1. 打开 https://github.com/new

  2. 填写：

        Repository name : minigal          ← 名字随意，记住它
        Description     : （可留空）
        Public / Private: ★ 选 Public       ← 必须公开
        Add a README file              : 不勾
        Add .gitignore                 : None
        Choose a license               : None

  3. 点 Create repository

  ★ 后三项务必都不要勾。
    勾了 README / gitignore / license 会生成一个初始提交，
    本地推送时需要先 pull 合并，凭空多出一道麻烦。
    建好后看到「Quick setup」页面（上面有仓库地址）就是对的。

  4. 从那个页面复制仓库地址，形如：

        https://github.com/<用户名>/minigal.git

     注意用 HTTPS 这种（不是 SSH 的 git@github.com:...）。
     SSH 需要配密钥，HTTPS 最多多输一次密码。

========================================================

在项目根目录执行（也就是包含 package.json 的 minigal 目录）：

  cd "C:/Users/24015/WorkBuddy/2026-09-15-15-57-04/minigal"

  git init

★ 顺序不要反：先 git init 再 remote add。
  反过来会报「not a git repository」。

--------------------------------------------------------
 自查（可选）
--------------------------------------------------------

在项目根目录执行：

  git -c core.quotepath=false status --porcelain --untracked-files=all

检查输出里有没有这一行（应当出现）：

  ?? dist/yaoguai/minigal/index.html

如果这一行没出现，说明被 .gitignore 挡了，去改 .gitignore。

★ 两个必加的参数，不加会误判：
  --untracked-files=all
      默认模式下，未跟踪的**目录**会被折叠成一行（只显示 `?? dist/`），
      看不到目录里的具体文件。我曾因此误以为「产物被忽略了」，
      其实是没展开。
  -c core.quotepath=false
      git 默认会把中文文件名转义成八进制（`"\345\257\274\345\205\245..."`），
      想按文件名找「导入到酒馆中/」这类路径时会匹配不到。

★ 有一条底线要记住：
  **dist/yaoguai/minigal/index.html 必须能进仓库。**
  反过来说，绝不要在 .gitignore 里写 `dist/` ——
  那样 CDN 上会 404，而你会以为「jsDelivr 坏了」。


========================================================
 第四步：首次推送
========================================================

先确认一下本地的默认分支名：

  git branch --show-current

  → 打印 master 或 main。**刚 git init 的瞬间也能用**（本机 git 2.54 实测）。

  如果它打印为空，用这条兜底：

  git symbolic-ref --short HEAD

★ 不要用 `git rev-parse --abbrev-ref HEAD`：
  在还没有任何提交的空仓库上它会报
  「fatal: ambiguous argument 'HEAD'」或打印 HEAD，拿不到分支名。
  而首次操作时你正好处在空仓库状态。

现在按分支名推：

  git add .
  git commit -m "chore: minigal 初始提交"
  git push -u origin master        ← 若上面显示 main，这里改成 main

★ 关于 master / main：
  正式版 json 里的 CDN 地址写的是 @master。
  如果本地默认分支是 main，有两条路——
    简单：把 json 里的 @master 改成 @main
    省事：把分支改名成 master（git branch -M master），两边一致
  两者不能混。地址写 @master 而仓库没有 master 分支 = 404。

  推送成功后再核对一次（这次一定准）：

    git branch --show-current
    git ls-remote --heads origin

★ 首次推送会要求登录 GitHub。
  用 HTTPS 方式推时，git 会弹出浏览器让你授权，或在终端索要
  「用户名 + Personal Access Token（不是账号密码）」。
  GitHub 从 2021 年起不再接受账号密码推送，只认 token。
  生成入口：https://github.com/settings/tokens
  选 classic → 勾 `repo` 权限 → 生成后复制那串字符当密码用。
  （如果弹的是浏览器授权页，按提示点确认即可，不用手搓 token。）

--------------------------------------------------------
 ★ 代理坑（本机实测过，你一定会遇到）
--------------------------------------------------------

这台机器上 GitHub 必须走代理（直连不通），全局 git 配置里是：

  http.proxy  = socks5://127.0.0.1:7897
  https.proxy = socks5://127.0.0.1:7897

**git 自身用 socks5 没问题，但凭据助手会崩。** 因为 Windows 上的
凭据助手（GCM）是基于 .NET 的，而 .NET 的 ServicePointManager
不认识 socks5 方案，实测报错：

  fatal: ServicePointManager 不支持具有 socks5 方案的代理。
  fatal: could not read Username for 'https://github.com': terminal prompts disabled

表现就是：拉代码（ls-remote / clone）一切正常，一到推送就卡住或报上面这串。
很容易误判成「token 不对」或「仓库权限不够」，其实压根没走到认证那一步。

★ 已做的修复（仓库局部覆盖，没动你的全局配置）：

  git config --local http.proxy  http://127.0.0.1:7897
  git config --local https.proxy http://127.0.0.1:7897

  同一个端口（7897）同时支持 http 与 socks5（Clash 类代理的常见行为），
  实测三条路径的结果：

    ① socks5://127.0.0.1:7897   git 传输通，但凭据助手崩
    ② 不走代理（直连）          不通
    ③ http://127.0.0.1:7897     通（git 传输 + 凭据助手都能用）

  所以只把方案从 socks5 换成 http，其余不变。全局配置保持原样，
  影响范围仅限本仓库；想撤销：

    git config --local --unset http.proxy
    git config --local --unset https.proxy

★ 如果推送时仍然卡住不动（不报错、也不结束）：
  那通常是凭据助手弹出了窗口在等你操作，或在等一个看不见的输入。
  Ctrl+C 中断，改用下面这条在你自己终端里跑（有交互式终端才收得到提示）：

    git push -u origin master

★ 若不想让助手弹窗，也可以直接用带 token 的地址推一次：

  git push https://<用户名>:<token>@github.com/doncain/galdemo.git master

  ★ 这条命令会把 token 写进 shell 历史，用完记得清理；仅在别无他法时用。

 第六步：验证 CDN 真的通了
--------------------------------------------------------

推完之后**不要立刻**去酒馆试——jsDelivr 对新提交需要几十秒回源。
先在浏览器打开那个 URL，或者用命令行核对：

  PowerShell:
    (Invoke-WebRequest "<你的CDN地址>").RawContentLength

  Node:
    node -e "fetch('<你的CDN地址>').then(r=>r.text()).then(t=>console.log(t.length))"

把打印出的字节数与本地产物对比，两者必须相等：

  PowerShell:
    (Get-Item "dist/yaoguai/minigal/index.html").Length

  Node:
    node -e "console.log(require('fs').statSync('dist/yaoguai/minigal/index.html').size)"

★ 字节数不等 = 推送的不是最新产物，或者 CDN 还在旧缓存。
  这时先重新构建 + 重新发布（见文末「日常更新」），再核对。


========================================================
 第七步：.gitattributes —— 别让 git 改产物的字节
========================================================

项目里已有一个 .gitattributes，**不需要你改**。它做一件事：

  dist/** -text

意思是「dist 下的文件按二进制处理，不做任何行尾转换」。

★ 为什么这条至关重要：

  我们的发布验证方法是**比较字节数**——
    本地文件的字节数  ==  从 CDN 拉回来的字节数
  相等才算发布成功。

  而本机 core.autocrlf=true。默认情况下 git 会在提交时把 CRLF 归一成 LF，
  取出时转回 CRLF。对源码这是好事，对产物是灾难：
  一旦发生转换，两个字节数就会差出「行数」那么多，
  而且看起来像内容损坏——你会以为发布失败，实际只是行尾被改了。

  实测：首次提交时产物恰好是 LF，所以字节数刚好一致。
  这是**碰巧，不是保证**——换个构建环境产出 CRLF 就会暴露。
  所以现在就钉死。

★ 自查（想确认的话）：

  git check-attr text -- dist/yaoguai/minigal/index.html
  → 应当打印 text: unset   （unset = 不做转换）

  再对比一下暂存区与本地的字节数是否一致：

  git cat-file -s :dist/yaoguai/minigal/index.html
  node -e "console.log(require('fs').statSync('dist/yaoguai/minigal/index.html').size)"

  两个数字必须相同。

 日常更新（以后改了代码要让玩家看到）
========================================================

项目里的 scripts/publish.mjs 已经把这件事自动化了，且带硬检查：

  ① npm run build                       构建
  ② node scripts/publish.mjs --dry-run  只检查，不提交（推荐）
  ③ node scripts/publish.mjs            检查 + 提交 + 推送
  ④ node scripts/verify-cdn.mjs         核对 CDN 拿到的是不是同一份
  ⑤ 需要立刻生效时，打开脚本给出的 purge 链接刷缓存
     （不刷则玩家最多 12 小时内自动拿到新版）

★ 第 ④ 步以前要手工做（publish.mjs 只打印命令），现在有脚本了。
  它从「正式版 json」里读 CDN 地址，所以地址一改它自动跟着改，
  不会出现「脚本查的地址与交付件不一致」的假通过。

  ★ 实测经验：purge 接口返回 `"status":"finished"` 之后，
    **边缘缓存还要几分钟才真正生效**。有一次 10 次重试（约 3 分钟）
    仍然拿到旧版，到第 4~5 分钟才更新。

--------------------------------------------------------
 ★★ 重要：CDN 地址必须钉提交号，不能用 @master
--------------------------------------------------------

这是本项目花了整整一轮才定位的坑，而且**表现极具欺骗性**：

  玩家（或你自己）看到的界面永远停在旧版，
  无论怎么清浏览器缓存、怎么 purge、等多久，都不变。
  而 CDN 返回的是 HTTP 200、字节数稳定——**看起来一切正常**。

根因：**jsDelivr 对「分支引用」的解析结果会被缓存，而且 purge 修不好它。**

  实测（同一时刻，同一个文件）：

    @master                     → 254502 B  ← 几轮之前的内容
    @36f80fc（提交号）           → 268811 B  ← 正确，且立刻可用
    @36f80fc34633e930...（完整）  → 268811 B  ← 正确

  响应头显示 `Age: 423`（边缘缓存 7 分钟前刚刷过）、
  `x-jsd-version-type: branch` —— 说明边缘是新的，
  问题出在 **jsDelivr 源站的分支解析缓存**。

  试过且**无效**的修法：
    · purge 文件路径      → 返回 finished，但内容不变
    · purge 分支本身      → 返回 finished，但内容不变
    · URL 加查询串 ?v=xxx → 内容不变（不参与缓存键）

  **有效的修法**：把 `@master` 换成 `@<完整commit-sha>`。
  提交号是**内容寻址**的，jsDelivr 把它当不可变对象，不会错。

所以：

  · 正式版 json 里的地址现在是 `@<commit-sha>` 形式，**这是刻意的**
  · `node scripts/publish.mjs` 会自动把地址钉到刚提交的那个 commit，
    你不需要手工改
  · **代价**：地址会变，所以每次发布后要在酒馆里更新那一行 URL
    （重导入 json，或直接编辑正则的替换串）
  · **开发迭代时请改用本机通道**（`minigal-界面-实时修改.json` + `scripts/serve.mjs`），
    它完全不经过 CDN，不存在这个问题

  `node scripts/verify-cdn.mjs` 会检查地址形式，是分支引用时会明确警告。

  ★ 只想查一次（CI 或快速确认）：

      node scripts/verify-cdn.mjs --once

  发布器会替你挡住三个常见事故：

  · 产物比源码旧（改了代码没重新构建）→ 拒绝发布
  · CDN 地址还是 REPLACE_ME → 拒绝发布
  · 地址用的是分支引用 → verify-cdn 会警告（见上一节）

★ 纪律：构建和发布不要串在同一条命令里。
  让构建完整跑完，再单独执行发布。
